## 1️⃣ Attention dilution — tool schema บัง summary

### อาการ
ผู้ใช้ถาม "เราเคยคุยเรื่องการอ่านไหม" รอสเต้ตอบว่าไม่เคย **ทั้งที่ summary ของบทนั้นถูก
recall มาอยู่ใน system prompt ครบถ้วน**

### การหาต้นเหตุ
ทดสอบ 4 ทาง พบว่าทุกทางแลกกันหมด:

| ทาง | ความจำ | ข้อมูลสด |
|-----|--------|----------|
| A ปัจจุบัน | 7/24 (29%) | 16/16 |
| B ไม่ส่ง tools | 23/24 (96%) | **0/16** |
| C ย้าย summary ใกล้คำถาม | 9/24 (38%) | 16/16 |
| D ย้าย + ไม่ส่ง tools | 24/24 (100%) | **0/16** |

**การย้ายตำแหน่ง summary ช่วยน้อยมาก (29%→38%)** — ระยะห่างไม่ใช่ตัวแปร **ขนาด**ต่างหาก

### ตัวแปรจริง: ขนาด ไม่ใช่เนื้อหา
- เกณฑ์อยู่ราว **3,700c**: tool รวม ≤3,607c ผ่าน 6/6 แต่ ≥3,707c เหลือ 0-1/6
- พิสูจน์ว่าไม่เกี่ยวกับ*เนื้อหา*: tool ปลอมที่ description เป็นตัว `x` ล้วนก็พังเท่ากัน
- ตรงกับที่งานวิจัยเรียกว่า *Over-Tooled Agent / Prompt Budget Starvation*
- `TOOLS` ทั้งก้อน = 4,292c จึงเกินเกณฑ์ทุกครั้ง

### ทางแก้: Dynamic tool selection
วัดด้วย pass^40 (n=120) + Wilson confidence interval:

| | ความจำ | ช่วง 95% | ข้อมูลสด | ขนาด |
|---|---|---|---|---|
| ยื่นครบ 6 ตัว | 30/120 (25%) | [18-33%] | 100/100 | 4,292c |
| **คัดด้วย keyword** | **120/120 (100%)** | **[97-100%]** | 100/100 | **725c** |

ช่วงไม่ซ้อนทับ = ต่างจริง และ tool accuracy ไม่ตกเลย

### บทเรียนเรื่องการวัด ⚠️
ที่ pass^8 (n=24) ผลสองรอบให้อันดับ **สลับกัน** (S2 100%>S1 96% แล้ว S1 100%>S2 92%)
เพราะความคลาดเคลื่อน ±8-10% กว้างกว่าช่องว่างที่กำลังเทียบ — **เกือบเลือกผิดเพราะอ่าน noise
เป็นสัญญาณ** ต้องดูช่วงความเชื่อมั่น ไม่ใช่ตัวเลขที่ดูสูงกว่า

📁 `tools/bench_attention.py`, `tools/bench_realistic_tools.py`

## 2️⃣ summary เก็บแต่หัวข้อ ไม่เก็บเนื้อหา

### อาการ
```
summary: "23 ก.ค.: คุยเรื่องความแตกต่างระหว่างเจลาโต้และไอศกรีม"
ผู้ใช้ถาม: "ผมชอบของหวานอะไร"  →  ตอบไม่ได้
```

### ต้นเหตุ: กฎที่เขียนไว้เอง
`memory.build_summary_prompt` สั่งว่า:
- `"ห้ามเติมชื่อหนังสือ/สถานที่/ตัวเลข/รายละเอียดที่ผู้ใช้ไม่ได้พูดถึง"`
- `"สั้นที่สุดเท่าที่จะบอกหัวข้อได้"`

บวก verify pass ที่ตามลบรายละเอียดอีกชั้น — **กฎกัน hallucinate เหวี่ยงเกิน จนห้ามทั้ง
ของแต่งขึ้นและของที่ผู้ใช้พูดจริง**

### เทียบ 6 วิธี (บทสนทนาจริง × 5 รอบ)

| วิธี | มาจาก | รายละเอียดผู้ใช้ | ระบุเจ้าของ | ขนาด |
|------|-------|------------------|-------------|------|
| A ปัจจุบัน | รอสเต้ | 30% | 60% | 57c |
| B ขอรายละเอียดตรงๆ | เซสชันนี้ | 60% | 100% | 145c |
| C ห้ามแบบระบุประเภท | **mindcraft** | 100% | 100% | 143c |
| D tags แยกชนิด | **ProjectBEA** | 100% | 100% | 106c |
| E C+D | — | 100% | 100% | 108c |
| **F แยกเจ้าของ** | **ไอเดียผู้ใช้** | 100% | 100% | 134c |

### เฟส 2: ใครชอบอะไร (ตัวชี้ขาด)

| วิธี | จำของผู้ใช้ | **จำของตัวเอง** | สลับเจ้าของ | **ถูกทั้งคู่** |
|------|-------------|-----------------|-------------|----------------|
| A | 0% | 0% | 0% | **0%** |
| B | 0% | 0% | 0% | **0%** |
| C | 0% | 0% | 0% | **0%** |
| D | 100% | 0% | **47%** | **0%** |
| E | 100% | 0% | 0% | **0%** |
| **F** | **100%** | **100%** | 13% | **87%** |

**F เป็นวิธีเดียวที่จำเรื่องตัวเองได้** — อีก 5 วิธีได้ 0%

**D (ProjectBEA) สลับเจ้าของ 47%** เพราะมีแต่ `user_*` ไม่มีที่เก็บเรื่องบอท โมเดลเลยยัด
ทุกอย่างลงฝั่งผู้ใช้ — รอสเต้จะเชื่อว่าผู้ใช้ไม่ถนัดสืบสวน ทั้งที่ผู้ใช้ชอบ

### รูปแบบ F
```
"1 ส.ค.: คุยเรื่องแนวนิยาย | user_pref:ชอบนิยายสืบสวน me_pref:ชอบแนวแฟนตาซี"
```
- `user_pref:` / `user_fact:` — เรื่องของผู้ใช้
- `me_pref:` / `me_fact:` — เรื่องของรอสเต้เอง

## 3️⃣ pipeline ความจำมี 3 ส่วน

```
1. บันทึก  →  2. อ่าน/ค้น  →  3. ส่งเข้า context  →  โมเดล
```

### ส่วนที่ 3: ส่ง — เทียบ 3 วิธี (n=100 ต่อวิธี)

| วิธี | ความจำ | ช่วง 95% | สลับเจ้าของ | ข้อมูลสด | context |
|------|--------|----------|-------------|----------|---------|
| P1 ยัดเข้า context (เดิม) | 58/100 | [48-67%] | 29 (29%) | 100% | 464c |
| P2 โมเดลค้นเอง (tool) | 36/100 | [27-46%] | 19 (19%) | 100% | 818c |
| **P3 กรองฝั่งก่อนยัด** | **88/100** | **[80-93%]** | **0** | 100% | **318c** |

**ทั้ง 3 คู่ต่างจริง** (ช่วงไม่ซ้อนทับ)

**P3 ชนะทุกมิติพร้อมกัน** — แม่นกว่า, สลับ 0, context เล็กสุด, เร็วสุด ไม่ได้แลกอะไรเลย

### ทำไม P2 (ให้โมเดลค้นเอง) แพ้
qwen3:8b เรียก `search_memory` แค่ **34/100 ครั้ง** และระบุ `whose` ถูก 14/34
ที่เหลือเดาคำตอบเองโดยไม่มีข้อมูล → แต่งเรื่องหนักกว่าเดิม

วัด 3 รอบได้ 24%, 34%, 36% — สม่ำเสมอ ไม่ใช่ความบังเอิญ
**เป็นข้อจำกัดของโมเดลเล็ก ไม่ใช่แนวคิดผิด** (production มี `forced_tool_calls` อยู่แล้ว
ด้วยเหตุผลเดียวกัน)

### ส่วนที่ 2: อ่าน/ค้น — ส่วนที่เกือบลืมวัด

bench ก่อนหน้า**ข้ามส่วนนี้ไปเลย** ป้อน summary ที่เขียนไว้ตายตัวให้ P1/P2/P3 หยิบตรงๆ
ตัวเลข 88% จึงสมมติว่าส่วนนี้ทำงานสมบูรณ์แบบ — ของจริงไม่ใช่:

| วิธี | ชุดปกติ | ชุดหิน | รวม |
|------|---------|--------|-----|
| ปัจจุบัน (`recall_summaries`) | 3/10 | 2/7 | **5/17** |
| **P3** | 10/10 | 7/7 | **17/17** |

**เจอ 2 ปัญหาที่ bench ก่อนหน้ามองไม่เห็น:**

1. **`PAST_HINTS` gate ตัดคำถามธรรมดาทิ้ง** — "ผมชอบอ่านอะไร" ไม่มีคำว่า "จำได้ไหม"
   → คืน `[]` ทันทีโดยไม่ค้นอะไรเลย ทั้งที่ข้อมูลอยู่ครบ (เป็นคำถามที่คนถามบ่อยที่สุด)
2. **ยัดทั้งบรรทัด** → ของอีกฝั่งปน 6/7 เคสที่ค้นเจอ

#### keyword vs vector — ตัวแปรหลักคือ "กรองฝั่ง" ไม่ใช่ "วิธีค้น"

วัดที่ n=81 (27 เคส × 3 รอบ) ทุกวิธีกรองฝั่งเจ้าของเหมือนกัน:

| วิธี | ผ่าน | ช่วง 95% | ชุดคำพ้อง | latency |
|------|------|----------|-----------|---------|
| keyword + กรอง | 69/81 (85%) | [76-91%] | 21/30 (70%) | **5 ms** |
| **vector + กรอง** | **81/81 (100%)** | [95-100%] | **30/30** | 1,213 ms |
| keyword→vector | 75/81 (93%) | [85-97%] | 27/30 | 199 ms |
| union | 81/81 (100%) | [95-100%] | 30/30 | 1,069 ms |

**การกรองฝั่งสำคัญกว่าวิธีค้นมาก** — ทั้งสองวิธีดีขึ้นมหาศาลเมื่อกรอง:
- keyword: ไม่กรอง 5/17 → กรอง 16/17
- vector: ไม่กรอง 7/17 → กรอง **17/17**

keyword แพ้เฉพาะ**ชุดคำพ้อง** (70%) เพราะ newmm ตัดได้ "เลี้ยงสัตว์" แต่ summary เขียน
"เลี้ยงแมว" — ไม่มีคำตรงกันเลย ส่วน vector ค้นด้วยความหมายจึงไม่ติดปัญหานี้

⚠️ **บทเรียนเรื่อง n ซ้ำอีกครั้ง**: ที่ n=17 ได้ keyword 16/17 vs vector 17/17 ต่างกัน
1 เคส จึงสรุปว่า "แยกไม่ออก" — พอเพิ่มเคสคำพ้องเป็น 10 อันและวัดที่ n=81 กลายเป็น
69 vs 81 **ช่วงไม่ซ้อนทับ = ต่างจริง** ชุดทดสอบเดิมมีเคสคำพ้องน้อยเกินกว่าจะเห็นจุดต่าง

#### เก็บ LLM rerank ไว้ (แม้ช้า)

profile พบว่า vector 1,070ms แบ่งเป็น embedding 399ms (37%) + chroma query **2ms** +
LLM rerank 668ms (62%) — การค้นจริงใช้แค่ 2ms เวลาหมดไปกับการเรียก Ollama

ทดสอบตัด rerank ที่ n=81:

| แบบ | ผ่าน | ช่วง 95% | latency |
|-----|------|----------|---------|
| มี rerank | 81/81 (100%) | [95-100%] | 1,223 ms |
| ไม่มี rerank | 78/81 (96%) | [90-99%] | 401 ms |

ช่วงซ้อนทับ (แยกไม่ออกทางสถิติ) **แต่ 3 ครั้งที่พลาดเป็นเคสเดียวกันหมด** — "เคยคุยเรื่อง
ฟุตบอลกันไหม" ที่ต้องตอบว่าไม่เคย embedding คืนของใกล้ที่สุดมาเสมอ ส่วน rerank เป็นตัวตัดทิ้ง

**`filter_by_owner` กรองว่า _ของใคร_ แต่ไม่ได้กรองว่า _เกี่ยวไหม_** — rerank ยังมีหน้าที่
เฉพาะตัว จึงเก็บไว้ ยอมรับ latency แล้วไปหาที่ลดจากส่วนอื่นแทน

📁 `tools/bench_memory_pipeline.py`, `tools/bench_memory_read.py`,
`tools/bench_memory_search.py`, `tools/bench_rerank_ablation.py`, `tools/memory_tool_proto.py`

## 4️⃣ บทเรียนที่ใช้ซ้ำได้

### prompt แก้พฤติกรรมโมเดลไม่ได้ — ต้องมี validation layer
ลองใส่กฎ "ห้ามเก็บคำที่รอสเต้บรรยายตัวเอง" ลง prompt → **ไม่ได้ผล** และหลุดในรูปที่แย่กว่าเดิม
ตรงกับที่โปรเจกต์เจอมาแล้ว 2 ครั้ง (`_strip_ungrounded_optional_args`, `fix_persona_slips`)

### อย่าจับคู่ประธาน+กริยา — กริยาไม่มีวันครบ
`guess_owner` รุ่นแรกจับ `รอสเต้ + ชอบ/สนใจ/ถนัด` → พังทันทีที่เจอ "ทำงาน"/"อ่าน"
เปลี่ยนเป็นจับ**ประธานอย่างเดียว** (ประธานนับได้ กริยาไม่มีที่สิ้นสุด)
บทเรียนเดียวกับ `_TOOL_REASONING_LEAK_RE` ที่เคยติดกับดัก whack-a-mole

### metric ที่วัดไม่ได้ผลแยกวิธี = ไร้ประโยชน์
`DETAIL_HINTS` รุ่นแรกให้ทุกวิธีได้ 100% รวมทั้ง A ที่สั้น 52c — เพราะนับแค่ว่ามีคำว่า
"ลึกลับ/นิยาย" ไหม ซึ่งอยู่ในชื่อหัวข้ออยู่แล้ว **ต้องออกแบบ metric ให้แยกวิธีออกจากกันได้**

### ตรวจข้อมูลดิบก่อนสรุปว่าเครื่องมือพัง
เคยรายงานว่า `find_ungrounded` พลาด "The Picture of Dorian Gray" — ตรวจแล้วพบว่า
**ชื่อนั้นอยู่ในบทสนทนาจริง** (เห็นแต่ preview ที่ถูกตัด) เครื่องมือทำงานถูก ผมอ่านผิดเอง

### เขียนชุดทดสอบเพื่อ *หาจุดพัง* ไม่ใช่เพื่อให้ผ่าน
ชุดปกติที่ออกแบบคู่กับวิธีแก้ → P3 ได้ 10/10 (ผ่านง่ายเกินไป)
ชุดหินที่ตั้งใจโจมตีจุดอ่อน → เจอบั๊กจริง 2 จุดทันที

## 5️⃣ latency ตอนใช้จริง — vector ไม่ใช่ตัวปัญหา

วัดผ่าน `chat.ask_ollama` เส้นจริง:

| ขั้น | เวลา | สัดส่วน |
|------|------|---------|
| **main_llm** (โมเดลคิดคำตอบ) | **3,534 ms** | **73.5%** |
| semantic_recall (vector) | 1,219 ms | 25.3% |
| tool_calls | 203 ms | 4.2% |
| รวม | 4,809 ms | |

**ตัวที่กินเวลาจริงคือ `main_llm` ไม่ใช่ vector** — ต่อให้ตัด vector ทิ้งทั้งหมดก็ลดได้แค่ 25%
การไปรีดเวลาจากส่วนค้นจึงไม่คุ้ม

ทางลดที่มีผลจริง: **ยิง `semantic_recall` ขนานกับขั้นตอนอื่น** แทนการ `await` ตรงๆ
([chat.py](../chat.py) ในลูป recall) จะซ่อน 1.2s ได้เกือบหมดโดยไม่ต้องตัดฟีเจอร์

⚠️ **บั๊กในการวัดที่เจอ**: รอบแรกรายงานสัดส่วนเกิน 100% (semantic_recall 212%) เพราะอ่าน
`stats.get_recent()[0]` ซึ่งเป็น record **เก่าสุด** (docstring บอกว่าใหม่สุดอยู่ท้ายลิสต์)
ทำให้เก็บค่ารอบแรกซ้ำทุกรอบ — ตัวเลขที่ผิดชี้ไปคนละทิศกับความจริง

## 6️⃣ สถานะ — ย้ายเข้า production แล้ว

**ทำครบ 3 ส่วนพร้อมกัน** (ทำแยกไม่ได้ผล):

| ส่วน | ไฟล์ | เปลี่ยนอะไร |
|------|------|-------------|
| บันทึก (F) | `memory.build_summary_prompt` | คืน JSON + tag แยกเจ้าของ |
| ค้น | `memory.recall_summaries` | กรองฝั่ง + แก้ gate |
| ส่ง (P3) | `chat.py` | กรอง vector ตามเจ้าของก่อนยัด |

### ⚠️ 7 ใน 8 เคสที่พลาดคือคำถามเดียวกัน — และไม่ใช่ปัญหาของระบบความจำ

คำถาม "รอสเต้ชอบอ่านแนวไหน" พลาดซ้ำๆ ด้วยคำตอบแบบ:
```
"ชอบแนวแฟนตาซีและนิยายสืบสวนค่ะ"     ← "สืบสวน" เป็นของผู้ใช้
"ชอบแนวแฟนตาซีและนิยายไซไฟค่ะ"      ← "ไซไฟ" ไม่มีในความทรงจำเลย
"ชอบแนวแฟนตาซีและเรื่องราวปริศนา"   ← "ปริศนา" ก็ไม่มี
```

**ตรวจแล้วพบว่าการกรองทำงานถูกต้อง 100%** — บล็อกที่ส่งเข้าโมเดลสะอาด:
```
keyword recall  → "— รอสเต้: ชอบแนวแฟนตาซี"          ไม่มี "สืบสวน"
vector ดิบ      → "user_pref:ชอบนิยายสืบสวน me_pref:ชอบแนวแฟนตาซี"
vector หลังกรอง → "— รอสเต้: ชอบแนวแฟนตาซี"          ไม่มี "สืบสวน" ✅
```
และ persona/fewshot ไม่มีคำว่า "สืบสวน"/"แฟนตาซี" เลยสักคำ

**สรุป: qwen3:8b ได้ข้อมูลถูก 1 อย่าง แล้ว _เติมอย่างที่สอง_ เข้ามาเองทุกครั้ง**
เป็นนิสัยการแต่งเสริมให้คำตอบดูสมบูรณ์ ไม่ใช่การจำสลับ — ที่บังเอิญตรงกับคำในความทรงจำ
ฝั่งผู้ใช้ทำให้ถูกนับเป็น "สลับเจ้าของ" ผิด

⚠️ **ปัญหานี้จะโผล่ทุกครั้งที่ความทรงจำมีข้อมูลน้อย** ไม่จำกัดแค่เคสนี้ แต่เป็นเรื่อง
persona/prompt ที่ต้องแก้แยก และมีอยู่ก่อนงานนี้แล้ว
